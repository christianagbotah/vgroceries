# Prisma model parity for recovered UAT migrations — 15 November 2026

**Scope:** Source-only repair on top of canonical main. Seven previously
applied UAT migration files were restored verbatim by PR #98. Those SQL
migrations must not be recreated, modified, dropped or marked rolled back.

This patch restores the missing Prisma schema representation for the historical
cashier role and shared session actor contract, StaffInvitation, PasswordResetToken, StockAdjustment,
CustomerSupportCase, CustomerSupportActivity and POS sale-time customer
identity. Model names, columns, defaults, indexes, relations and decimal types
are copied from the branch where those exact migration files originated.

**Important reconciliation:** The source branch predates newer staff pickup
attendance work. This change retains the canonical PickupAttendanceRecord
model and its User, Order and LogisticsNode relations. Copying the old schema
over the new one would silently remove an already-applied attendance table
from Prisma's model.

No migration file, database row, user permission, application operation,
environment flag, feature route, payment, refund or stock balance is changed.
This model repair alone does **not** activate the unfinished cashier, support,
inventory, recovery or pickup workflows.

## Validation and deployment gates

- Run Prisma validate and Prisma generate against the updated schema.
- Run TypeScript no-emit and the targeted regression
  test/prisma-uat-model-parity.spec.ts after compilation.
- Run both GitHub CI workflows with fresh isolated PostgreSQL.
- Compare Prisma migration diff on an isolated restored UAT database to ensure
  **zero unintended DROP TABLE, DROP COLUMN or constraint removal**. Inspect
  the result; do not apply it automatically.
- Check read-only Prisma migrate status on protected UAT against the verified
  history and checksums.
- Merge only after a reviewed no-drift outcome; stage with backup and rollback.
  Production public storefront remains Coming Soon.

**Prohibited during this change:** Prisma db push, migrate reset,
autogenerated destructive migrations, changes to _prisma_migrations, any
real financial transaction or automatic enabling of POS, customer pickup or
SMS functionality.

See issues #99 and #64 and migration history documentation for the separate
runtime feature and physical pickup acceptance gates.
